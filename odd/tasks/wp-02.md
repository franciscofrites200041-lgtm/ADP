# WP-02: Database foundation

## Goal
Provide the Drizzle/PostgreSQL foundation for the product-owned data model, migrations, an idempotent seed mechanism, integration-test support, and PostgreSQL-backed API readiness.

## Decision
REQ-3 requires database tables for users, workspaces, providers, API keys, agents, conversations, and messages. Better Auth owns its user/workspace tables and remains WP-03 scope. WP-02 implements the product-owned §7 tables, including provider credentials, API tokens, agents, conversations, and messages.

## Scope
- New `packages/db` Drizzle schema, migration runner, migrations, and idempotent seed mechanism.
- All product-owned tables from MIDDLEWARE_MASTER.md §7, excluding Better Auth tables.
- PostgreSQL integration coverage is deferred: Testcontainers is cancelled for this and all remaining work by user instruction.
- PostgreSQL ping in API `/readyz`.

## Out of scope
- Better Auth tables and account flows (WP-03).
- The six concrete agent templates (WP-21).
- Docker Desktop or live Compose/Caddy smoke tests.

## Tasks
- [x] T1 Map package conventions and establish the database package contract.
  - Added `@middleware/db`, application-generated UUIDv7 IDs, and strict package conventions.
- [x] T2 Define the product-owned Drizzle schema and generate an initial migration.
  - All 23 §7 product-owned tables, required constraints/indexes, and initial Drizzle migration are present.
- [x] T3 Add migration runtime and idempotent seed mechanism with unit tests.
  - Testcontainers and all container-based testing are cancelled by user instruction; real PostgreSQL proof is deferred.
- [x] T4 Extend API readiness to verify PostgreSQL connectivity with tests.
  - `/readyz` uses an injected database ping and returns 200 on success, 503 on failure/rejection; `DATABASE_URL` is validated at the API boundary.
- [ ] T5 Run applicable checks, native review, and record evidence per work unit.

## Acceptance criteria
- Generated migration is structurally verified and `db:generate` is idempotent; applying it to a clean database is deferred because container-based testing is cancelled.
- Real PostgreSQL integration that inserts and reads every product-owned table is deferred because Testcontainers is cancelled.
- `/readyz` returns 200 only when PostgreSQL is reachable.
- Every business table has indexed, non-null `workspace_id`; repositories accept it first when introduced.

## Evidence
- `packages/db`: focused tests, typecheck, and lint passed for schema, migration artifact, runtime, CLI, and seed mechanism. The generated migration contains 23 product-owned tables and regenerates without changes.
- `apps/api`: focused tests, typecheck, and lint passed for injected PostgreSQL readiness behavior and `DATABASE_URL` validation.
- Deferred by user instruction: Testcontainers, Docker/Desktop, live PostgreSQL connection/migration application, and database integration tests.
